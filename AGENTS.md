# Правила и ограничения при работе с проектом mdoc

## Общее описание

mdoc - это текстовый конвертер MarkDown формата. Предназначен для упрощённого конвертирования
без применения сложных проектов вроде pandoc.

## Структура директорий

- в корне только:
    - md - исполняемый файл
    - lib - директория со всеми используемыми модулями
- lib/txt.pm - отвечает за текст и координаты в исходнике.
- lib/prs.pm - собственный Markdown/YAML-парсер.
- lib/out - директория с модулями рендеринга в нужные текстовые форматы (html/pdf)
- doc - директория с документацией
- test - директория с тестовыми исходными документами

Взаимодействовать с файлами и папками вне основной директории проекта (mdoc) нельзя. Вся работа только внутри.

## Запуск и проверка работы

Для выполнения конвертирования необходимо выполнить:

```bash
./md [options] source destination
```

- source - исходный md-файл
- destination - файл, в который нужно выполнить конвертирование

Формат файла destination определяется по расширению или через параметр: -t, --type

## Тестовые документы

- тестовые Markdown-документы размещаются в директории `test`
- имя файла должно отражать проверяемый синтаксис или сценарий
- `test/md-syntax.md` содержит примеры всех поддерживаемых конструкций Markdown и должен обновляться при изменении синтаксиса парсера
- тестовый документ должен быть самостоятельным и пригодным для запуска через `./md`
- результаты тестового конвертирования сохраняются в директории `test/result` и после проверки не удаляются
- результаты конвертирования не являются тестовыми исходниками и не должны добавляться в репозиторий
- в файле md-syntax.md содержатся поддерживаемые конструкции и модификаторы
- в папке unsupported/ находятся md-файлы с неподдерживаемыми конструкциями
- по мере доработки конвертера неподдерживаемые ранее конструкции следует переносить из unsupported/ в md-syntax.md
- при доработках функционала и исправлении багов парсинга md-файлов рекомендуется добавлять в эту папку файлы с исследуемой конструкцией, чтобы на этих файлах проверять результат доработки и исправления

## Требования к изменениям файлов

- не менять содержимое файла, если этого не требует поставленная в чате задача
- там, где правки определены поставленной задачей, менять файлы только в тех местах, где требует задача, остальное содержимое не менять, даже если оно не соответствует перечисленным правилам
- для css, js, html и perl файлов tab-отступы: 4 пробела
- не делать рефакторинг существующих файлов, только делать необходимые правки, исходя из поставленной задачи
- при выполнении правок, сохранять стилистику и форматирование написания файлов
- структура файлов и имена файлов не должны меняться без необходимости
- по завершению выполнения задачи необходимо перечислить все изменённые файлы и описать изменения, сделанные в этих файлах

### Требования к perl-коду

- по возможности используем существующие функции, методы и модули
- при модификации функции метода необходимо скорректировать её описание

- требования к формату коментариев в коде:

    - описание модуля целиком

        пример:

            =pod
                ======================================================================
                    Заголовок и краткое назначение модуля одной строкой
                ======================================================================
                    Подробное описание,

                    которое может быть многострочным.

                    В этой части может находится длинное описание особенностей,
                    если таковые есть, сложности выполняемых задач,
                    способы их реализации.
                ======================================================================
            =cut

    - отделение целого блока внутри модуля, возглавляющее какой-то набор методов и функций

        пример:

            # ----------------------------------------------------------------------
            # ---
            # ---   Краткое описание блока
            # ---   Оно может (но не обязано) быть многострочным
            # ---

    - ключевые методы и функции модуля, работающие как вход и выход, требующие подробного описания

        пример:

            # ----------------------------------------------------------------------
            # ---
            # ---   имя функции/метода
            # ---
            # Подробное описание,
            # которое чаще всего является многострочным
    
    - функции и метода, выполняющие простые рабочие задачи

        пример:

            # Краткое описание. Здесь не требуются дополнительные отступы и заголовки,
            # только описание, которое может быть многострочным
    
    - ключевые блоки внутри функции

        пример:

            # Подробное описание блока. Чаще всего
            # оно многострочное.
            #
            # Абзацы следует отделять пустой строкой.
            #
            # Такие коментарии обычно описывают какие-то сложные особенности
            # при работе в текущем месте кода.
        
    - в случае серьёзных модификаций, важных переделок, смены парадигмы, часто при лечении каких-то багов

        пример:

            ## Такие коментарии чаще всего являются многострочными. И их следует выделить
            ## каким-то уникальным способом.
            ##
            ## Внутри следует описать, как работало до изменения, что стало причиной изменения
            ## и почему пришлось сменить парадигму работы. Например, почему пришлось изменить
            ## порядок следования функций, почему это важно.

    - простые комментарии в коде - над строкой с комментируемым кодом

        пример:

            # небольшое описание, что мы делаем
            call($arg1, $arg2);
    
    - описание вызываемых аргументов - только если их много и требуется перечислить

        пример:

            call(
                $arg1,      # описание arg1
                $arg2,      # описание arg2
                $arg3,      # описание arg3
                $arg4       # описание arg4
            );
        
        Начало коментария должно быть выровнено отступами в 4 пробела. Комментарии всех аргументов
        данного вызова должны быть выровнены вертикально.

    - если в коде встречается case (или if/else) конструкция с 3 и более вариантами, в каждом варианте описывать комментарием суть этого варианта

- требования к именам переменных, функций и методов:

    - только маленькие буквы (применение больших букв иногда допустимо, но должно быть обоснованно)
    - дляна не должна быть большой, суть должна быть сосредоточена в пределах 3-8 символов
    - чем более локальные функции решает переменная, функция или метод, тем её название короче
    - названия можно сокращать, если это не уменьшает понятность, например: $process -> $proc
    - если внутри класса требуется реализовать внутреннюю функцию без передачи самого объекта, такую функцию следует называть с подчёркиванием в начале
    - если функция или метод предполагает только внутреннее использование, то имя должно начинаться с подчёркивания

- стандартные короткие имена переменных:

    - $h = heigth
    - $w = width
    - $x = координата X
    - $y = координата Y
    - $name = имя
    - $s или $str = строка
    - $url = ссылка обычным текстом
    - $fmt = format
    - $img = image
    - $ctx или $c = context

- если хеш или массив локальный и ему нет необходимости быть ссылкой, то лучше его делать нативным хешем или ссылкой

    если нет необходимости делать так:

    ```
    my $hash = {};
    $hash->{key} = '...';
    my $array = [];
    push @$array, '...';
    ```
    
    то лучше делать вот так:

    ```
    my %hash = ();
    $hash{key} = '...';
    my @array = ();
    push @array, '...';
    ```

- условный оператор ? ( <condition> ? 'true' : 'false' )

    - в скобки берём только составные элементы, если это требуется. Всё условие целиком в скобки брать не следует.
    - если оба варианта значений длинные или вариантов более двух (более одного условного оператора), то следует переносить строки с отступом, например:

    ```
    my $var1 = $condition ?
        'long string is true' :
        'long string is false';
    
    my $var2 =
        $cond < 10 ?
            'value < 10' :
        $cond < 100 ?
            '10 <= value < 100' :
            'value >= 100';
    ```

#### файл lib/prs.pm

- глобальные данные документа, которые известны в момент разбора элемента, следует
  собирать во время основного прохода парсера. Контейнер для них нужно создавать в `doc()` рядом с
  остальными данными документа и явно передавать по цепочке вызовов до распознающей функции. Не следует
  добавлять отдельный рекурсивный обход готового дерева только для повторного сбора таких данных. Дополнительный
  проход допустим только для обработки, которой необходим полностью разобранный документ; причину такого прохода
  нужно описать в коде


### Правила генереции MarkDown

- у таблиц должны быть выровнены вертикальные линии
- содержимое ячеек таблиц должно быть выровнено согласно выравниванию в колонке
